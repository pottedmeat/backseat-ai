a workflow in the back seat, nagging your agent through every step

Structure and direction for your coding agent, enforced.

Graph-based workflows for coding agents.

A workflow is a graph: states, the transitions between them, and the instructions for each. The agent you already use drives it from its own shell: it reaches a state and is told what to do there and which transitions are open, and anything else is refused with a reason. A long prompt describes the steps; this holds the agent to them.

A workflow (a machine, in the code) is a TypeScript file in your project, driven through a small CLI (cli.ts, written into the project for you) from Claude Code, pi, opencode or whichever coding agent you use. The agent's commands are the ones under --drive. Nothing runs between calls.

The green signs on this page are snippets of one real workflow. A coding agent drives it, though the work is research: a lead agent that cuts a question into sub-tasks, sends a subagent, a worker, after each, and writes up what comes back.

I've seen how you drive without me

A workflow that is enforced, not described.

Backseat came from wanting more from workflows that ran on instructions alone. Each was a long prompt describing the steps, and even a frontier model treated it as a description: mostly followed, never enforced. The want was a workflow that holds its shape whichever model is in it.

So the shape is written down and enforced. You decide what can happen: the states, the transitions out of each, the guard on each one (a condition that has to hold before it is offered), the schema it must be sent with. The model decides what does. The workflow is semi-deterministic: the steps and the routes between them are fixed, and the model's judgment fills the rest, what it does inside a step and, where more than one transition is open, which one it takes.

It is LangGraph with the roles reversed. A framework like LangGraph drives inference calls: your code calls the model at each node and reassembles the messages and context for the next. Backseat drives a conversation: the agent you are already talking to runs one command, reads what the workflow says, does the work with its own tools, and asks again.

What is enforced is the path. The workflow cannot stop an agent from walking away, and it does not see how the work was done. It never advances on anything but a transition it offered, sent with a payload that passed.

A model handed one step at a time, with its instructions and its schema, and refused with a reason when it strays, runs a workflow it could not have run from the prompt. It does not have to be a frontier model. Because each response carries only one state's instructions and data, a smaller model has a short, specific prompt at every step instead of one long one to keep in mind.

I'll tell you everything, once we're on the road

The agent reads nothing before it starts and, even then, only what it needs.

Most agents start under a wall of instructions: every rule, every step, every case, read before anything has happened and carried through everything after. Here there is nothing to read first. The agent starts the workflow as an actor, a running instance with an id of its own, and from then on it is told what it needs when it needs it: what to do in the state it is in, which transitions are open from there, and nothing about the rest of the workflow until it gets there.

don't worry, I wrote it down

The workflow keeps the ledger; the agent is read the part it needs, where it needs it.

Everything the workflow knows lives in one ledger (context in the code): the question, the round it is on, the sub-tasks still queued, the findings so far, each kept as it was written for as long as the run lasts. A transition writes to it; a state reads from it. A state declares data: the part of the ledger the agent is handed while it is there, computed each time it arrives. A line written on the third call reads the same on the sixty-ninth, sixty-six calls and six workers later, so the agent is shown the ledger, not its recollection of it. What a state does not declare stays hidden.

the agent sees arriving at planning with the round and the budget of rounds, and nothing else: the question stays in the ledger

I'll tell you what to do when we get there

Instructions arrive with the state, not before it.

Every state and every transition carries a one-line description: a clarification of what it is, read while the agent is choosing. There are no instructions in it. Instructions are what a state hands the agent by being reached. So the agent commits to a transition before it reads a word of what it will be asked to do there, and the instructions for the roads not taken never enter its context. A state's instructions are also told which visit this is. The first visit explains the whole job; every return, with that explanation still in the agent's context, gets one line that points back to it.

the workflow a one-line description on a transition and on a state, and instructions that differ between the first visit and a return
the agent sees, while choosing the next state offered in two lines of description, with no instructions in them
the agent sees, on arrival the full instructions, handed over only once the worker is in the state

we're not taking the exit until you say which one and why

Every transition is a checkpoint: the agent proves it has what the next state needs.

The agent takes a transition by sending its event, and the schema is what that event has to carry, its payload: printed under the transition while the agent is still choosing, so the proof is never a guess. It can be computed from the ledger, so what a checkpoint asks for can depend on where the run is.

the workflow two ways out of a state, each with the schema its event has to carry
the agent sees both schemas printed under their transitions, then a finding that passes and ends the worker's run

hold on, I've got a gadget for that

The workflow brings its own tools, and uses them on the way.

Some of the work in a workflow is not the agent's to do: a lookup, a call to a service, a judgment the workflow would rather make itself. Backseat puts that work on the transition, as an effect: it runs when the agent takes the transition, after the checks have passed. Whatever the tool brings back is attached to the event as its output, and the author decides what of it goes into the ledger and what goes straight to the agent. The agent sends the event and reads what came back; it never holds the tool.

the workflow an effect that asks a small scoring model how many rounds the question warrants, and where its answer goes
the agent sees the budget the effect judged, with its reason, on arrival at planning

I looked it up. they're closed

Some reasons to refuse only turn up mid-transition.

While a guard can keep a transition from being shown, some reasons to refuse are only found partway through the transition: an effect, or an action writing to the ledger, finds one and says so in the author's words. The workflow rejects the event with that message, says the actor has not moved, and prints the arrival again, so the next call is the corrected one.

the workflow an effect that checks each cited source and rejects the event when one is gone

the agent sees · the worker's finding, refused on a source that is gone

here's who to call and what to tell them

The workflow lists the subagents; the agent starts them.

A subagent that needs a workflow of its own gets one, with a ledger of its own. The agent makes the call. It starts the subagent and tells it to run the listed command, which hands the subagent a workflow of its own, and that is the whole handoff, because once in the seat the subagent has a backseat driver of its own, with its own instructions, its own refusals and its own ledger, told only its input. While the subagents work, the agent carries on through the workflow. The first transition that needs what they produce is not offered until all of them have finished; sent anyway, it is refused, naming the subagents still out. Sent once they are back, it brings their work into the parent's ledger at the workflow's discretion. Only what the calling agent needs is surfaced to it.

the workflow a state that starts a subagent's workflow on arrival, and a transition held until every subagent has finished
the agent sees arriving at researching with a subagent to start and the command to hand it
the third subagent sees the subagent's own first arrival after running that command: its sub-question and the question it was cut from, nothing else of the parent's

sit down, I made a slideshow of the trip

Every call is in the trace, and the report walks you through it.

Every call an agent makes lands in the trace: the state the actor was in, the transition it took or was refused and the reason, and what an effect brought back. The trace report draws each actor's journey from it, the states it stopped in and the calls answered from each. A run is assessed from the workflow's trace, never from the agent's account. That is how a workflow improves: a wrong turn sits under one state, so the instructions to fix are that state's. Fix them, run again, and the next report says whether it worked.

One prompt, and the back seat is taken.

Paste one of the prompts at the top into your coding agent and you run nothing yourself: it installs the companion skill, runs init, and writes the workflow with you. To run the workflow, tell your agent to run node cli.ts --drive create <machine> and to follow what it prints. By hand, the one command is init: it sets the directory up as a project and, with no machine to find in your source, offers a starter: one state, one transition, then finished. Run it again any time; it finishes what is missing and leaves the rest alone. Every command is in the CLI reference.
