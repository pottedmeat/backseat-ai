# A transition may run the tool it guards, and its output reaches the agent only through the event

Backseat guards the order of a workflow. A workflow that leaves its tools outside the machine leaves the most-called surface ungoverned: in one XState-guarded workflow with its own CLI, three calls in four went to a side tool the machine could not see, and so did most of the usage errors. The machine could not refuse a read made in the wrong state, validate its parameters, or know which reads happened. Had each tool call been a transition, the refusals Backseat already has would have applied as they stand: `not-enabled` in the wrong state, `invalid-payload` with the schema shown, and the trace as the read log. What was missing was a way for a transition to do the I/O and hand back what it found.

**A transition under `on` may carry `effect: ({ context, event }) => value | Promise<value>`.** The runtime awaits it inside the `send` that names the actor, after every check has passed in its usual order (the actor is active, the event enabled, the spawned children settled, the payload validated, a transition selected) and before any collection bookkeeping and before XState sees the event. What it resolves to is put on the event as `output`, after validation, as `settled` is ([ADR-0008](0008-an-actor-never-changes-under-its-driver.md)). The transition's actions read `event.output` and decide what the machine keeps; the landing state's `data` reads it and decides what the agent sees. There is no third channel back to the agent.

- **Refusal is an action's refusal** ([ADR-0007](0007-an-action-may-refuse-the-event-it-runs-for.md)). An effect that throws `RejectedEvent` answers `refused` with its message; anything else it throws answers `action-failed`. The actor does not move, and since the effect runs before anything durable changes, there is nothing to unwind.
- **An effect is a move.** A transition with an effect and no target and no actions, a read whose output only `data` shows, is offered and taken, where XState alone would treat it as forbidding the event.
- **`data` is handed the event once.** `data` is `({ context, event }) => unknown`, and `event`, with `output` and `settled` on it, is present only on the response to the `send` that carried it. A rejection, `snapshot`, `describe` and `create` pass none, so nothing looks as if it ran. Nothing is persisted for this.
- **`output` is reserved.** A schema written as a value that declares `output`, on a transition or on a state, fails registration. Validation already drops an undeclared key, so an agent cannot supply one, and the effect's value is written over whatever a context-derived schema may have accepted.
- **An effect belongs on an event an agent sends, and nowhere else.** On `always`, `onDone` or any other key it would run while the driver is away, the change [ADR-0008](0008-an-actor-never-changes-under-its-driver.md) forbids. The types refuse it on `always` (`AnEffectRunsOnlyOnAnEventAnAgentSends<'effect'>`); registration refuses it on every key no agent sends, for a machine written in raw XState. `invoke` stays refused: an effect is run inside the call that names the actor, which an invoke is not.
- **`output` is declared on the event type, and that is what types it.** With `{ type: 'note.read'; id: string; output: Note }` in the union, the actions and `data` see `event.output` as a `Note`, the effect must return one, and a transition on that event without an effect does not compile. A guard and the effect itself see the event as sent (`Sent<Ev>`, without `output`), since the guard chooses the transition before the effect runs. We tried inferring `output` from the effect's return type instead; TypeScript does not carry a sibling property's return type into `actions` under `createMachine`'s single `const` inference, and declaring it is how XState types an invoked actor's `onDone` output too.
- **The trace records the output whole.** `TraceEntry.effect` carries `{ output }` for every call whose effect ran and returned, including one whose transition an action then discarded, beside the response that showed only what `data` chose.

The name is XState's: `invoke`'s `onDone` receives what the invoked promise resolved to as `event.output`, and an effect is an invoke run inside the call.

**Writes are not rolled back.** A writing effect can succeed and an action after it refuse or throw; the transition is discarded, the actor stays, and the write stands. So the effect is where a writing transition does its refusing. A second phase after XState accepts the transition would still leave a crash between the write and the save, so it buys less than it costs.

**The `data.<key>` check declines on keys an effect supplies.** Registration evaluates `data` against a context and no event, so a key derived from `event.output` is absent there by construction. The check tolerates a missing key only on a projection an effect's transition can land on (its target, or its source when it has none), so a machine with no effects is checked in full. Supplying a sample event per state would close the gap at more cost to every author than the gap is worth.

We rejected a separate channel for tool output beside `data`, which would need its own once-only rule, check and rendering, and persisting the output for `data` to read from context, which is the hidden context [ADR-0002](0002-context-hidden-except-declared-data.md) exists to prevent.

The costs: an agent can still call the underlying tool directly, which this does not stop. Two `output`s exist, an actor's and an effect's (the glossary's **effect output**). An effect runs inside the root's lock, so children driven in parallel queue behind each other's I/O. The Stately export does not draw an effect; it tags the state `effect:<event>`, and `may-refuse:<event>` where the effect throws `RejectedEvent` ([ADR-0010](0010-the-stately-export-is-a-view.md)). A read that loops back to its state reprints the state's moves on each call, which [ADR-0016](0016-a-move-shown-whole-is-then-named.md) shortens.
