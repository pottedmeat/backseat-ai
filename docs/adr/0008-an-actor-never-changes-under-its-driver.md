# An actor never changes under its driver

A driver reads a response, decides, and sends ([ADR-0001](0001-cli-targets-agents-not-humans.md)). If the actor could move between two of its calls — because a child finished, a timer fired, or another agent's call reached it — the response it last read would be quietly untrue, and the trace would hold a move nobody chose. Spawned children are where this pressure comes from: they finish whenever they finish, and a parent needs to say "not until the workers from there are back".

**An actor's state and context change only during a call that names it. A parent learns of its children by asking, never by being pushed. A transition that needs a spawn site's children back gates on them with `collectChildren(state, machine, ...actions)`: taking it collects every child that settled there, hands their outcomes to `actions` as `event.settled`, and stops them. While any child of the site is still running, the transition is not offered.**

## Nothing moves an actor behind its driver

Every `on` key no agent can send is refused: a child's `xstate.done.actor.*` and `xstate.error.actor.*`, the runtime's own `agent.*`, a bare `*` and a partial wildcard like `task.*`. TypeScript refuses them where they are written (`NotAnEventAnAgentCanSend<K>`), and `validateMachine` repeats the check at registration for a machine written in plain XState. The wildcards are refused on the key itself because XState's `EventDescriptor<E>` contributes `'*'` and every partial prefix whatever the author's event union says, and inside `on` a wildcard is weight only internal events can reach: it blocks an ancestor's transitions and swallows the `onDone` a compound state is left by. A key outside the machine's own event union is refused under its own name (`NotAnEventThisMachineDeclares<K>`), because XState's excess-property check misses a misspelled event on any state that handles a second one. `after` and `invoke` are refused for the same reason; no process exists for a timer to fire in ([ADR-0003](0003-cli-rehydrates-per-invocation.md)).

A crashed child is collected, not fatal. XState relays a child's failure to its parent and, unhandled, takes the parent down with it, so the runtime absorbs `xstate.error.actor.*` itself, in `agentTracking.on`, with no target and no actions. That is the only shape of the key the check accepts. With these refused, one call moves exactly one actor.

## The gate owns the lifecycle

`collectChildren` lowers to `meta.settled` on the transition. The runtime files each child, after the call that spawned it, under the matching site among the transition's source and entered states, since XState records nothing about where a child came from. A spawn the lowering cannot see — a `spawnChild` inside an action's body — is filed from the child's own `src` and the state the call started from, and collected like any other; only a child with no `src` at all cannot be, and that is a warning.

Taking the gate, in order: verify every child of the site has settled, copy each one's outcome into the run record, hand the collection to the actions, then stop the children. The actions receive the agent's own event with `settled` added after payload validation — `[{ state, src, children: [{ actorId, status, output?, error?, about? }] }]` — so XState processes no event the agent did not send. `about` is what the parent said the child was for when it spawned it (the child's input, if it said nothing), filed at the spawn and persisted with the site, because a child that ended in `error` or `stopped` has no `output` and is already gone by the time the collection is read. Stopping is what makes "settled" mean "no longer among its parent's children"; since `stopChild` deletes the child from the persisted snapshot too, `backseat-ai output <childId>` reads the copied record. Being collected does not clear a site — two transitions waiting on one site both see it — but the next spawn there does, which keeps one round's workers out of the next round's collection. An action that throws on a collecting transition is unwound, the children left uncollected and unstopped, and answered `action-failed`, so the same event can be sent again.

A spawn site no transition collects is a registration error: its children's results would be discarded in silence. Two sites of one `src` reachable from one transition are refused too, because a child could not be filed under one.

## A move not offered now is not shown

A transition whose sites still have a child running is left off the list — on an arrival, a `snapshot`, a rejection and a bare `describe <actorId>` alike — and sending it, or asking `describe <actorId> <event>` for it, is refused as `pending-children`, naming each running child. Once every child has settled it is listed, with a `Requires:` line. A move whose guard fails is never listed either, and sending it is refused with `that event is not offered from the current state, <state>, right now. Send only an event listed below.` When nothing is offered, the moves block says `No move is offered until your subagents finish their workflows.` if a move is held back for children, and `No move is offered from here right now.` otherwise.

We chose this over a guard (invisible, and indistinguishable to the agent from a transition that does not exist) and over an `always` that moves when the last child finishes (the actor changing under its driver). We rejected listing a waiting transition and refusing it at send: it shows an agent a move it cannot take, and a driver that sees a move listed reads it as on offer.

The costs: the runtime adds a key, `settled`, to an event the agent sent; a spawning state whose only move is the collecting one lists nothing while its children run, so its instructions must name that move and say it comes once the children are back; the list a driver was given can change between two of its calls, as children settle, without its actor having moved; and a machine cannot use the wildcards XState and Stately Studio treat as first-class.
